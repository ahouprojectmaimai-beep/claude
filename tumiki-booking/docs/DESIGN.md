# TUMIKI 日程調整・自動予約システム 設計書（STEP 1）

## 1. 技術選定（維持費・運用の軽さ優先）

| 項目 | 採用 | 理由 |
|---|---|---|
| 実行環境 | Cloudflare Workers（+ 静的アセット） | 無料枠で運用可。サーバー管理不要。HTTPSが標準 |
| API | Hono | 軽量・型安全 |
| DB | Cloudflare D1（SQLite） | 無料枠で十分。1文が原子的に実行され二重予約防止に使える |
| 定期処理 | Workers Cron（10分ごと） | 外部変更の同期漏れ拾い・期限切れ仮押さえ掃除・通知チャンネル更新 |
| 画面 | ビルド不要の素のHTML/CSS/JS | スマホで軽い。改修が簡単 |
| カレンダー | Google Calendar API（fetch直接） | 公式REST仕様に準拠。依存ライブラリなし |
| メール | Resend（標準）/ Gmail API（切替可） | 独自メール。Googleの招待とは役割分担 |
| 認証 | Google OAuth 2.0（管理者のみ） | お客様はログイン不要 |

月額: 0円〜（Resendも月3,000通まで無料）。独自ドメインを使う場合のみドメイン代。

## 2. 画面構成

### お客様（`/`）― スマホ最優先・1画面で完結
1. TUMIKIロゴ・「お打ち合わせのご予約」「ご都合の良い日時をお選びください」「所要時間：約60分」
2. 開催方法（3択カード）: オンライン(Meet) / 対面(事務所) / 対面(店舗・指定場所)
   - 事務所: 登録済み住所を表示
   - 店舗・指定場所: 店舗名（必須）・住所（任意）を入力。住所が空なら「住所未確認」として管理者に表示
3. 日付（月カレンダー。予約不可日はグレーで選択不可）
4. 時間（空きを一覧表示。15分刻みが初期値）
5. お客様情報（お名前*・メール*・会社名/店舗名・ご相談内容）＋個人情報の利用目的
6. 予約内容の確認 → 7. 「予約を確定する」→ 完了画面（ロゴ・日時・方法・場所/Meet・変更/キャンセルリンク）

### 予約管理（`/manage?b=…&t=…`）― ログイン不要・トークン
予約内容の確認 / 日時変更（最新の空きを再取得）/ キャンセル

### 管理画面（`/admin`）― Googleログイン（管理者メールのみ）
- 予約一覧（日時・お客様・会社・方法・場所・状況・住所未確認・カレンダー外部変更の印）、変更、キャンセル、再通知
- 予約設定（曜日・時間帯・枠長・刻み幅・期間・当日可否・締切・前後余裕・事務所住所・場所の決定者）
- Google連携（接続状態・接続/再接続/解除・空き判定カレンダー選択・登録先選択・通知チャンネル状態）
- メール履歴（失敗の確認と再送）

## 3. データベース（`migrations/0001_init.sql`）

- `bookings` … 予約本体。`start_ts/end_ts`（UTC秒）、`block_start_ts/block_end_ts`（前後余裕込み）、`status`（pending / confirmed / cancelled / failed）、`event_id`、`meet_url`、`manage_token_hash`、`location_*`、`address_unconfirmed` など
- `settings` … 予約設定のJSON（1行）
- `google_account` … 管理者のGoogleアカウント。**リフレッシュトークンはAES-GCMで暗号化**して保存
- `sync_state` … カレンダー差分同期トークン、通知チャンネル情報
- `mail_log` … メール送信履歴（失敗・再送管理）
- `rate_limits` … 簡易レート制限

## 4. 空き時間の判定

```
空き = Googleカレンダーが「予定あり」でない時間（終日含む）
       ∩ 当システムの未キャンセル予約と重ならない時間（前後余裕込み）
       ∩ 管理者設定（曜日・開始/終了時刻・期間・当日可否・締切）
```
- 登録先カレンダー: `events.list` で取得（本人のカレンダーなので詳細を見られる。自分の予約を除外して「変更」の空きを出せる）。「予定なし（transparent）」「辞退」「キャンセル」は除外
- 追加の判定対象カレンダー: `freeBusy` API
- 開始時刻は設定の刻み幅（5/10/15/30分…）で生成し、**どの開始時刻でも枠長ぶん連続で空き**が条件
- お客様には空き時間以外（予定名・参加者）を一切返さない

## 5. 二重予約防止・競合検出（最重要）

3段構えにする。

1. **DB側の原子的な仮押さえ**: 重なりの無い場合のみ `INSERT ... WHERE NOT EXISTS (重なる pending/confirmed)` を1文で実行。D1は1文が原子的なので、同時リクエストは片方だけが成功する
2. **Google側の最終確認**: 仮押さえ後に空きを再取得。直前に外部から入った予定があれば失敗扱い
3. **作成後の競合検出**: イベント作成後に再度重なりを確認し、他の予定と重なっていればイベントを削除して失敗扱い

整合性:
- イベントIDは予約IDから決定的に生成（`events.insert` を再実行しても重複しない。409なら既存を採用）
- カレンダー登録に失敗 → 予約は `failed`（確定扱いにしない）。途中まで作ったイベントは削除
- 仮押さえ(pending)が5分を超えて残っていたら、cronがイベントの有無を確認して後始末
- メール送信失敗は予約を取り消さない（予約は確定のまま、`mail_log` に失敗を記録し管理画面から再送）

## 6. 外部変更の同期

- **通知**: `events.watch` のチャンネルを登録（Webhook → `/api/google/webhook`、チャンネルトークンで検証）。期限前に自動更新
- **定期同期**: 10分ごとに `syncToken` で差分取得（通知の取りこぼし対策）。410なら全件再同期
- Googleで削除 → 予約を `cancelled`（`cancelled_by=calendar`）、時刻変更 → 予約の日時を更新（外部変更フラグ）
- 比較してから更新するので、通知とcronが重複しても・自分の更新が戻ってきても安全（冪等）

## 7. セキュリティ

- OAuth/APIキー等の秘密情報は Workers Secrets のみ。画面・Gitには出さない
- 管理画面: Googleログイン → `ADMIN_EMAIL` 一致のみ許可。署名付きHttpOnly Cookie。状態変更APIはOrigin検証
- 変更/キャンセルリンク: 256bitのランダムトークン（DBにはSHA-256のハッシュのみ保存、定数時間比較）
- 不正予約対策: IPごとのレート制限、ハニーポット項目、入力検証、同一メールの未来予約数上限
- 個人情報: 予約画面に利用目的を表示。Googleイベントにはお客様の氏名・メール・会社名・備考のみ
- 日時: 内部はUTC保存、表示と日付判定は `Asia/Tokyo`（Intlでゾーン換算するのでサマータイム地域にも拡張可）

## 8. デザインルール

`public/css/tokens.css` に色・角丸・余白を一元定義し、予約画面/管理画面/メールで共通利用。
ロゴは `public/brand/logo.svg` を差し替えるだけ（形・色・比率は変えない）。
