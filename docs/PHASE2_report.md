## 3. テストで見つかり、設計に反映したこと
- **2つのAIが日計表の金額を同じように読み間違えると、検算のない店舗では小銭の残額を誤って記録しうる**（例：小銭が後日入金になる京大前店）。
  → 書式を登録する店舗は、**レジ精算票の検算（金種合計・在高実績−翌準備金など）の設定を必須**にした。未設定ならシステムが起動しない。
- 通帳の1行目（前の行がない行）は残高検算ができないため、照合対象がその行なら要確認になる（新しいページの1行目など）。

### 実画像から見つかり、修正したこと
1. **funfo は0枚の金種を「-」と印字する** → 「読めない」ではなく0円として扱うように修正（直さないと、ほりまるは毎回判読不能になっていた）
2. **通帳の「繰越」行**（日付が「**-**-**」、お預り欄に口座番号が印字される）→ 残高だけを次の行の検算の起点に使えるようにした。口座番号らしき数字列は保存前に伏せ字にする
3. **新しい通帳の1行目が繰越で、入金と同じ日付**（京大前 9/29）→ お預りが空欄の行は入金候補から外し、要確認にならないよう修正（直さないと要確認になっていた）
4. **振込（楽天ペイ・PayPay）やポイントの入金**が通帳に混ざる → 銀行ごとに「売上の入金として扱う摘要」（ATM / ATM通帳 / 預金機）を設定し、それ以外の入金は照合に使わないようにした
5. 実データで小銭のルールを再確認：ほりまる・京大前とも、金曜・土曜分の小銭は月曜にまとめて入金され、日曜分は月曜にお札と小銭を一緒に入金していた（設定どおり）

## 7. 追記（2026-10-03）安いAIを優先する方針
- 方針：**精度の基準を満たす中で最も安いAI**を採用する（まいまいさん承認）
- 安全面：AIが安くなっても、2系統の一致・通帳の残高検算・レジ精算票の検算は変わらない。安いAIの読み間違いは「OK」ではなく「要確認」が増える方向に出る。そのため「要確認の多さ（手間）」と「費用」のバランスで選ぶ
- 比較するモデル（安い順）：Haiku 4.5（$1/$5）→ Sonnet 5.5 effort=low → Sonnet 5.5 effort=medium →（参考）Opus 5.5
- 暫定の本番設定：**Haiku 4.5 ＋ Sonnet 5.5(low) の2系統**（別々のモデルにすると、誤読が重なりにくい）。1枚あたり約10円前後、月 約2,000円の見込み（比較で確定）
- 比較コマンド：`npx tsx scripts/benchmark-models.ts --yes`（実画像12枚 × 4モデル、概算 約530円。`--yes` なしなら費用表示のみ）
- 採用基準：「自信ありの誤読」が0件、かつ主要項目・通帳行の正解率が高い中で最安
