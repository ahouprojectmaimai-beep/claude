| # | 調査項目 | 結論 | 根拠 |

| 1 | 通常LINEグループの「ノート」をAPIで取得 | ❌ **できない** | Messaging APIのWebhookイベント一覧・APIリファレンスにノート関連のイベント／エンドポイントが存在しない |

## 2. LINE公式APIの調査結果（詳細）

> 調査方法：LINE Developers 公式ドキュメント（developers.line.biz）を検索で参照。
> ※ この作業環境からは developers.line.biz への直接アクセスがネットワーク制限で遮断されていたため、公式ページの検索抜粋に基づいています。
> 「できる」と判断した項目は、**PHASE 3で実際のチャネルを使って実機検証してから**本番設計を確定します。

### 2-1. ノート・コメント（❌）
- Messaging APIのWebhookイベントは「メッセージ／送信取消／編集／友だち追加／ブロック／参加(join)／退出／メンバー参加・退出／ポストバック…」等。**ノート・アルバム関連のイベントは存在しない**。
- APIリファレンスにもノート／ノートコメントを読むエンドポイントはない。
- 公式に取得手段がない以上、「ノート運用を続けたまま自動化」は**不可能**と判断します。

### 2-2. 通常トークの画像・テキスト（✅）
- 公式アカウント（Bot）がグループに参加していれば、グループ内のメッセージ（テキスト・画像）はWebhookで受信できる。
- 画像はメッセージIDを使ってコンテンツ取得APIでダウンロードできる。
- **重要な制約**：
  - 「ユーザーが送ったコンテンツは一定期間後に自動削除され、保存期間は保証されない」→ **受信したら即座に自社ストレージへ保存**する設計にする。
  - Botが**参加する前のメッセージ（過去ログ）は取得できない**。
  - 複数画像を同時送信すると `imageSet`（index/total）付きで**別々のイベントとして順不同**で届く。
- 重複対策に使える公式ID：`webhookEventId`（再送でも同じ値）、`deliveryContext.isRedelivery`（再送フラグ）、メッセージ `id`。

### 2-3. 結果通知（✅、ただし料金に注意）
- プッシュメッセージはユーザー・グループ・複数人トークに送信可能。
- **通数カウント＝送信先の人数**（例：5人のグループに1回送る＝5通）。
- **応答メッセージ（Reply）は通数にカウントされない（無料）**。→ 受付確認・読み取り結果の返信は無料で送れる。
- LINE Notify は **2025年3月31日でサービス終了済み**。公式の代替はMessaging API。

### 2-4. 料金プラン（LINE公式アカウント）
| プラン | 月額 | 無料メッセージ通数 |
|---|---|---|
| コミュニケーション | 0円 | 200通/月（超過送信不可） |
| ライト | 5,000円（税別） | 5,000通/月 |
| スタンダード | 有料 | 上位 |

通数試算：
- 例）既存グループ20人に毎日2回（18時・19時）通知 → 20×2×30＝**1,200通/月 → ライト必須（5,000円/月）**
- 例）**管理者用の小グループ（3人）**に毎日2回 → 3×2×30＝**180通/月 → 無料プランで収まる**
- 店舗スタッフへの受付返信は Reply なので **0通**。

→ **最終報告は「管理者3名程度の通知用グループ」に送る**のがコスト的に最適。

## 4. 代替案の比較（3案）

### 案A：既存グループにBotを招待し、ノート→「通常トーク」に投稿
- スタッフ：グループに「白梅町」とテキスト＋写真を送る
- 課題：
  - テキストと写真は別メッセージ → 「同じ人が直前に送った店舗名」で紐付ける推測が必要
  - 後日小銭の「どの営業日分か」を特定する仕組みがない（金額・日付からの推測になる）
  - グループが写真で流れて、雑談・他の連絡と混ざる

### 案B（推奨）：公式アカウントとの1:1トーク＋リッチメニュー ＋ 既存グループにもBot参加
- スタッフ：公式アカウントを友だち追加 → 画面下のボタン **［白梅町］［聖護院］［京大前］［同志社前］［ほりまる］［小銭追加］［廃油］** をタップ → 写真を送る
- Botが即返信（無料）：
  ```
  ✅ 京大前店 10/2営業分 受付しました
  日計表：65,320円 ／ 入金：65,000円
  → 小銭320円は後日入金待ちとして記録します
  ```
  読めなかった場合：`⚠️ 金額が読み取れませんでした。通帳の数字が見えるように撮り直してください`
- 小銭追加：［小銭追加］→ 対象営業日の候補（未完了のものだけ）がボタンで出る → 選んで写真送信 → **推測ではなく確定で紐付け**
- 事務員の「現金チェックOK」・廃油投稿：既存グループのまま（Botが読むだけ）
- 最終報告：管理者用小グループへプッシュ

### 案C：Webフォーム（LIFF または Googleフォーム）
- スタッフ：フォームを開く → 店舗選択 → 写真アップロード → 送信
- 構造化は最も確実だが、Googleフォームの写真アップロードはGoogleログイン必須、LIFFは開発量が増える。スマホでの操作ステップも増える。

### 比較表

| 項目 | 案A 既存グループ通常トーク | **案B 1:1＋リッチメニュー（推奨）** | 案C Webフォーム |
|---|---|---|---|
| スタッフの操作量 | ◎ 店舗名入力＋写真 | ◎ ボタン1タップ＋写真 | △ フォーム入力＋写真 |
| 現在運用からの変更量 | ◎ 小（ノート→トーク） | ○ 中（送り先が変わる） | △ 大 |
| 画像取得の確実性 | ○ 紐付けに推測が入る | ◎ 送信者・店舗が確定 | ◎ |
| 過去分の追加入金対応 | △ 金額・日付から推測 | ◎ 営業日をボタンで指定 | ◎ |

## 5. 推奨アーキテクチャ

### 5-1. 構成要素

| 役割 | 採用サービス | 理由 |
|---|---|---|
| LINE受信・送信 | LINE公式アカウント（Messaging API） | 唯一の公式手段 |
| Webhookサーバー・定時実行 | **Cloudflare Workers**（有料プラン $5/月） | 常時HTTPS、署名検証可、Cron Triggers（18時・19時）、Queues、低コスト |
| 処理キュー | Cloudflare Queues | AI解析（数十秒）をWebhook応答と切り離す・自動リトライ |
| 正本データベース | **Cloudflare D1（SQLite）** | 一意制約・トランザクションで**二重加算を物理的に防止** |
| 画像保存 | Cloudflare R2（非公開バケット） | LINE側画像は消えるため即保存。保存期限ルールを設定 |
| 閲覧・集計用 | **Google Sheets（DBから自動ミラー、閲覧専用）** | 皆が見慣れた画面で履歴確認・月次集計 |
| 要確認の確認・修正画面 | 簡易管理画面（Workers）＋ **Cloudflare Access**（指定メールのみログイン） | 画像と抽出値を並べて「承認／修正」できる |
| 画像解析AI | Claude（Anthropic API）を第1候補、他社と実画像で比較して確定 | §8参照 |

> **なぜGoogle Sheetsを「正本」にしないか**
> Sheetsには一意制約・トランザクションがなく、Webhook再送や同時処理で**同じ入金が二重に記録される事故**を構造的に防げません。また誰でもセルを書き換えられるため監査ログの改ざん耐性もありません。
> そこで「**正本はDB、Sheetsは見る用のコピー**」とします。普段見る画面はSheetsのままで、使い勝手は変わりません。

## 6. データフロー

### 6-1. 通常の売上入金（案B）
1. スタッフ：［京大前］タップ（ポストバック）→ 写真送信
2. Webhook：署名検証 → `webhookEventId` で重複チェック → 画像を即R2保存（sha256算出）→ キュー投入
3. AI抽出：日計表（店舗名・営業日・入金対象額…）と通帳（各行の日付・入金額・残高・摘要）を構造化JSONで抽出
4. 検証ルール（プログラム）：§8-3のチェックを全部通過しないものは「要確認」or「画像判読不能」
5. 紐付け：`(店舗, 営業日)` の日次レコードを作成/取得。入金は「通帳の行」単位で `deposits` に登録
6. 照合（プログラム、店舗ルールは設定値）：
   - `bank_total == target_amount` → OK
   - 店舗の小銭ルールが「後日入金」かつ `bank_total == floor(target/1000)*1000` → 後日入金待ち（残額＝小銭）
   - 店舗の小銭ルールが「事務員確認」（同志社前）かつ お札部分一致 → 入金OK＋小銭：事務確認待ち
   - それ以外 → 要確認（差額を表示）
7. Reply：スタッフへ受付＋読み取り結果を即返信
8. 監査ログに「なぜその判定か」（使った値・ルール名・バージョン）を保存

### 6-2. 小銭の後日入金（京大前・ほりまる）
1. ［小銭追加］→ 未完了の営業日だけがボタン表示（例：`9/30 残320円`）→ 選択 → 写真送信
2. 通帳から該当入金行を抽出 → `deposits` に追加（**同じ通帳行は残高付きの指紋で一意**＝二重加算しない）
3. 累計入金を再計算 → 差額0なら「完了」→ 19時レポートの【過去分更新】に掲載
4. 一定日数（設定値、例：7日）を過ぎても残額があれば「要確認」に格上げ

### 6-3. 同志社前の事務員確認
1. 既存グループの通常トークで「9/28〜9/30分 現金チェックOK」を受信
2. **正規表現（プログラム）で期間を解析**。解析できない書き方はAIに渡さず「要確認」として管理者に提示
3. 送信者が「事務員として登録されたユーザーID」か確認（他の人の発言では更新しない）
4. 期間内の同志社前の営業日を「最終確認完了」に更新。メッセージID・送信者・本文・受信日時を証跡保存

### 6-4. 廃油
1. ［廃油］ボタン or 既存グループに受取書＋通帳写真
2. 受取書（日付・本数・金額）と通帳（「油入金」行の日付・金額）を抽出
3. `受取書日付 == 通帳入金日 && 受取書金額 == 通帳金額` → 油入金OK、それ以外 → 要確認
4. 投稿がない日は何もしない（未提出扱いにしない）

### 6-5. 18:00／19:00
- 18:00：各店の「今日提出されるべき営業日」（店舗カレンダー設定から算出）に提出があるか判定 → 未提出リスト確定（将来：該当店へリマインド送信を設定ONで追加可能）
- 19:00：キュー残りを処理 → レポート生成 → 管理者グループへ送信。同じ日のレポートは**送信済みキーで二重送信しない**

```
  target_table, target_id, field, old_value, new_value, reason, corrected_by, corrected_at

  at, actor(system|user), action, entity, before_json, after_json, reason

notifications       送信済みレポート（日付×種類 UNIQUE で二重送信防止）
```

### ステータス定義
| 総合ステータス | 意味 |
|---|---|
| ✅ OK | 入金確認済み（同志社前は「お札入金OK」） |
| 🟡 後日入金待ち | 京大前・ほりまるの小銭残（待機期限内） |
| 🟡 事務確認待ち | 同志社前の小銭（事務員確認待ち） |
| 🔵 最終確認完了 | 小銭含め全て確認済み |
| ⚠️ 要確認 | 金額不一致・紐付け不明・AI2系統不一致など |
| 📷 画像判読不能 | 必須項目が読めない／confidence不足 |
| ❌ 未提出 | 期限までに提出なし |

### Google Sheets（閲覧用ミラー）

## 8. AI画像解析方式

### 8-1. 役割分担
- **AI：画像 → 構造化JSON（値・confidence・根拠となる読み取り文字列）だけ**
- **プログラム：一致判定・差額計算・ステータス決定のすべて**（AIに「一致している？」とは聞かない）

### 8-2. モデル選定方針
- 第1候補：**Claude Opus 5.5**（Anthropic、Vision＋構造化出力、入力$4/出力$20 per 100万トークン）
- PHASE 2で実画像（正解値付き20〜50枚）を使い、次を**同じ評価セットで実測比較**して確定：
  - Claude Opus 5.5 / Claude Sonnet 5.5（$2/$10）
  - Google Gemini（最新版）
  - OpenAI（最新Visionモデル）
  - OCR専用サービス（Google Document AI 等）＋ルール抽出
- 評価指標：金額・日付の**完全一致率**、誤読時に「自信あり」と答えてしまった率（最重要）、JSON出力の安定性、1枚あたりコスト、応答時間
  ※ 他社モデルの価格・精度はこの資料作成時点で未検証のため、PHASE 2の実測値で判断します

### 8-3. 誤読でOKになることを防ぐ多重チェック（False Positive対策の要）
1. **2系統独立抽出**：異なるモデル（または異なるプロンプト）で2回抽出し、金額・日付が**完全一致した場合のみ**自動判定へ進む。食い違えば「要確認」
2. **通帳の残高検算**：`前行残高 + 入金額 == 当行残高` が成り立たない行は採用しない（AIの読み間違いを数式で検出できる強力なチェック）
3. **日付の妥当性**：入金日 ≥ 営業日、かつ営業日+N日以内（店舗設定）。未来日付は不可
4. **店舗クロスチェック**：ボタンで申告した店舗と、画像内の店舗名（読めた場合）が矛盾したら要確認
5. **金額の妥当性**：店舗ごとの過去実績レンジから大きく外れたら要確認（OKにはしない）
6. **confidence閾値**：必須項目のconfidenceが閾値（設定値）未満 → 画像判読不能
7. **手書き数字**：手書き項目は自動OKの根拠に使わない（設定で切替）

→ どれか1つでも失敗すれば自動OKにしない。**「分からないものは要確認」をコードの構造で保証**します。

### 8-4. コスト概算（AI）
- 1枚あたり：Opus 5.5で約5〜8円程度 × 2系統 ＝ 約10〜16円（実測で確定）
- 1日 約5〜8枚 × 30日 ≒ **月 2,000〜4,000円程度**（Sonnet採用なら約半分）

## 9. 重複処理防止（idempotency）

| 層 | 仕組み |
|---|---|
| Webhook再送 | `webhook_event_id` UNIQUE。再送は無視 |
| 同じメッセージ | `line_message_id` UNIQUE |
| 同じ画像の再投稿 | `sha256` UNIQUE → 既存画像として扱いスタッフに「既に受付済み」と返信 |
| 別写真に同じ通帳行が写る | `passbook_fingerprint`（口座・日付・金額・残高）UNIQUE → 二重加算しない |
| 再計算 | 累計は毎回 `deposits` から**集計し直す**（足し算を積み上げない）→ 何度実行しても同じ結果 |
| レポート二重送信 | `notifications(date, type)` UNIQUE |

## 10. セキュリティ設計

- 秘密情報（LINEチャネルシークレット・アクセストークン、APIキー、Googleサービスアカウント鍵）は **Cloudflare Secrets（環境変数）** に保存。コード・Gitには一切入れない（`.gitignore`＋コミット前チェック）

- ログに金額・口座情報を出さない（IDとステータスのみ）
- 事務員の「現金チェックOK」は登録済みユーザーIDからのみ有効
- Google Sheetsは特定アカウントのみ共有、リンク共有OFF。サービスアカウントは対象シート1枚のみ編集権限
- AI APIへの画像送信：各社のAPIデータ取扱い規約（学習利用の有無・保存期間）をPHASE 2で確認し、条件を満たすものだけ採用

## 17. v1.1 追加設計（実画像の分析＋回答の反映）

> 実画像の具体的な金額・残高は、銀行情報保護のためリポジトリには記載しません（チャット上でのみ共有）。ここでは、そこから導いた**設計ルール**だけを記録します。

### 17-1. 確定した業務ルール
| 項目 | 内容 | 設計への反映 |
|---|---|---|
| 入金対象額 | レジ精算の **「預入金」** | 抽出対象 |
| 小銭 | 1,000円未満の端数 | `お札 = floor(預入金/1000)*1000`、`小銭 = 預入金 − お札` |
| 土日祝 | お札は翌日、小銭は翌平日 | お札の予定入金日＝営業日の翌日、小銭の予定入金日＝営業日より後の最初の銀行営業日（祝日はデータで管理） |
| 投稿場所 | 1つのグループに全店舗が投稿。店名は必ず入る | 推奨案を案A'に変更（17-3） |
| ボヤけた画像 | 弾く。OKにしない | 必ず「画像判読不能」にする（17-4） |

### 17-2. 実画像から導いた設計ルール
1. **年の表記が書類によって違う**：通帳は和暦の2桁（例：08＝令和8年）、廃油の受取書は西暦の下2桁。年の解釈は書類の種類ごとに設定で決め、AIに推測させない。
2. **銀行によって通帳の書式が違う**（日付の区切り文字や列の構成）→ 店舗ごとに通帳の書式を設定で持たせる。
3. **通帳の残高検算**（前の行の残高＋お預り−お支払＝この行の残高）は、実画像の全行で成り立った → 誤読を見つける仕組みとして採用。透かし文字が数字に重なっている画像でも、この検算で守れる。
4. **レジ精算の内部検算**：金種の合計＝在高実績、在高実績−翌準備金＝預入金 → 通帳の検算と合わせて二重にチェックする。
5. **1枚の通帳写真に過去の取引行が多数写る** → 今回の営業日に対応する行を選ぶ。一度割り当てた行は（日付・金額・残高の組み合わせで）二重に使わない。
6. **連休明けは、複数営業日分の小銭が同じ日に別々の行で入金される**ことを実データで確認した。祝日の営業分は、翌日が平日ならお札と小銭が1行で入金される。
   → 小銭の行は、その店舗の「小銭待ち残額」と**金額で照合して自動で割り当てる**。候補が複数あって決められない場合は「要確認」にする。
7. 決算利息・引き出しの行がある → 照合するのは「お預り」列で、摘要がATM入金等の行だけ。
8. **廃油は同日入金とは限らない**（祝日をはさむと次の銀行営業日になる）→ ルールは「入金日＝受取日、または受取日より後の最初の銀行営業日」（期間は設定値）。
9. **油入金の行は、通帳の印字だけではATM入金と区別できない**（手書きメモが目印）→ 金額・日付の範囲・手書きメモで特定し、区別できなければ「要確認」にする。
10. 廃油受取書の金額は手書きで、書く欄が決まっていない → 「手書き金額」として抽出する。

### 17-3. 推奨案の変更：案A'（1つのグループ＋店名必須）
| 心配だった点 | 解決策 |
|---|---|
| テキストと写真が別々のメッセージで届く | 同じ投稿者の数分以内の「○○店」と写真を組にし、画像内の店名とも照らし合わせる。食い違い・店名なしは「要確認」 |
| 後日小銭の営業日特定 | 17-2の6の金額照合で自動で割り当てる |
| 雑談との混在 | 店名を含まないテキストは無視。画像はAIで「日計表＋通帳／廃油＋通帳／その他」に分類する |
| 撮り直しの依頼 | 問題がある投稿にだけ、元の投稿を引用して返信（Replyは無料）。正常な投稿には返信しない |
| 19時レポートの通数 | 送り先のグループの人数で費用が決まる → 管理者用の小グループ（無料）か、同じグループ（ライトプランが必要になる場合あり）かを選ぶ |

※ 投稿は「ノート」ではなく「通常トーク」で行う必要があります。

### 17-4. ボヤけた画像の扱い
- 金額・日付の項目ごとに「全桁がはっきり読めるか」をAIに判定させ、1桁でも曖昧なら **画像判読不能**
- 2つの方式で別々に読み取り、1桁でも食い違えば **画像判読不能／要確認**
- 残高検算・レジ精算の内部検算が成り立たなければ **要確認**
- 判読不能のときは、Botが投稿を引用して撮り直しを依頼する。撮り直し写真が届いたら同じ営業日として再処理する（前の写真も記録に残す）

### 17-5. テスト画像の扱い
- 実画像・正解値はGitにコミットしない。非公開のGoogleドライブフォルダで受け取り、テストのときだけ読み込む。
